# Доработки авторизации на фронтенде

Нужно завершить интеграцию с существующим API авторизации и привести код к правилам из [AGENTS.md](AGENTS.md).

## 1. Доменная архитектура

- [ ] Разнести функциональность по структуре `frontend/src/app/domain/<name>/{ui,service,repository}`.
- [ ] В `ui` оставить формы, представление, взаимодействие с пользователем и навигацию.
- [ ] В `service` разместить бизнес-правила и выполнение пользовательских сценариев.
- [ ] В `repository` определить интерфейс репозитория и общие DTO его контракта. HTTP-репозиторий должен реализовывать этот интерфейс и подключаться через Angular DI.
- [ ] Для каждого слоя определить собственные DTO и явно преобразовывать данные на границах. HTTP DTO держать внутри HTTP-адаптера.
- [ ] Убрать прямые HTTP-вызовы из сервисов и работу с хранилищем авторизации из UI-компонентов.
- [ ] Убрать `any` и соблюдать остальные правила типов, читаемости и exports из `AGENTS.md`.

## 2. Общий HTTP-клиент

- [ ] Реализовать общий `HttpClient` в `frontend/src/app/core/http/` поверх Angular `HttpClient`. Различать их через псевдоним импорта.
- [ ] Добавить типизированные методы `get`, `post`, `put`, `patch`, `delete`.
- [ ] Определить интерфейс `HttpRequestOptions` с поддерживаемыми настройками, включая `headers`, `params`, `withCredentials` и `isPrivate?: boolean`.
- [ ] Применять настройки к фактическому запросу. При повторах сохранять метод, адрес, тело, заголовки и параметры. Не передавать `isPrivate` на сервер.
- [ ] По умолчанию использовать `isPrivate: true`: добавлять актуальный access token для своего API и обрабатывать `401` через обновление сессии.
- [ ] Для login, register и refresh явно задавать `isPrivate: false`. Не добавлять им Bearer-токен автоматически и не запускать refresh при их `401`.
- [ ] Не передавать токены приложения на сторонние адреса и не запускать для них обновление сессии.
- [ ] Перевести HTTP-репозитории на общий клиент.

### Обновление токена и повторы

- [ ] При `401` приватного запроса выполнить `POST /auth/refresh`, сохранить новый access token и повторить исходный запрос с ним.
- [ ] Ограничить повторы: первоначальная попытка плюс максимум **3 повтора исходного запроса**. Счётчик относится ко всему логическому запросу и не сбрасывается при клонировании или повторной подписке.
- [ ] Для параллельных запросов использовать одну общую операцию refresh на приложение. Все ожидающие запросы должны получать её результат или ошибку.
- [ ] Новые приватные запросы, начатые во время refresh, должны дождаться его завершения перед отправкой.
- [ ] Если запоздалый `401` пришёл для старого токена, а новый уже получен, повторить запрос с новым токеном без дополнительного refresh. Этот повтор тоже учитывается в лимите.
- [ ] Сохранять новый токен до возобновления ожидающих запросов. Освобождать общую операцию после успеха или ошибки, чтобы последующие обновления могли выполняться.
- [ ] Сам refresh должен обходить механизм автоматического обновления, исключая рекурсию и бесконечные циклы.
- [ ] При `401` от refresh очищать состояние авторизации и один раз перенаправлять на `/login` для всех ожидающих запросов.
- [ ] При сетевой ошибке или временной ошибке сервера во время refresh передавать ошибку ожидающим запросам, не объявляя сессию отозванной.
- [ ] Не выполнять автоматические повторы обычных запросов при ошибках валидации, `403`, сетевых ошибках и `5xx`.
- [ ] Избежать циклической зависимости между общим HTTP-клиентом и auth-репозиторием: выделить механизм состояния сессии и координации refresh, а для самого refresh использовать транспорт без автоматического восстановления авторизации.

## 3. Контракты API и cookie

- [ ] Исправить payload регистрации: отправлять только `email`, `username`, `displayName`, `password`. Поле `confirmPassword` оставить в UI. Сейчас оно отправляется на сервер, который запрещает неизвестные поля и отвечает `400`.
- [ ] Типизировать ответ login/register/refresh: `{ user, accessToken, tokenType, expiresIn }`. Поле `expiresIn` измеряется в секундах.
- [ ] Убрать ожидание `refreshToken` в JSON-ответе и его хранение в `localStorage`: бекенд устанавливает его через HttpOnly cookie.
- [ ] Для login, register, refresh и logout включить `withCredentials: true`.
- [ ] Вызывать `POST /auth/refresh` без refresh token в теле: браузер передаёт cookie автоматически.
- [ ] Проверить соответствие адреса фронтенда настройке бекенда `FRONTEND_ORIGIN`. Эндпоинты авторизации и CORS уже реализованы.

## 4. Восстановление сессии, guard и выход

- [ ] При запуске приложения восстанавливать авторизацию через refresh. Наличие строки access token в хранилище само по себе не подтверждает действующую сессию.
- [ ] Guard маршрута `/chats` должен дождаться проверки или восстановления сессии и перенаправлять на `/login`, если авторизация отсутствует.
- [ ] После успешного входа или регистрации переходить на `/chats`.
- [ ] При выходе вызывать `POST /auth/logout` с Bearer-токеном и cookie, чтобы сервер отозвал сессию и очистил refresh cookie. Затем очищать локальное состояние и переходить на `/login`.
- [ ] Удалить прямую очистку токенов из компонента чатов и перенести управление сессией в соответствующий механизм авторизации.

## 5. Валидация и ошибки форм

- [ ] Согласовать ограничения с бекендом: пароль — **8–128** символов, email — до **254**, username — **3–32**, displayName — **1–80** после удаления пробелов по краям.
- [ ] Для username учитывать нормализацию: удалить пробелы по краям, привести к нижнему регистру, разрешать только `a-z`, цифры и `_`.
- [ ] У email удалять только пробелы по краям, сохраняя регистр. Пароль не обрезать и не изменять.
- [ ] Обновить сообщения об ограничениях и сохранить проверку совпадения паролей.
- [ ] Показывать понятные ошибки API внутри формы: неверные данные входа, занятый email или username, ошибки полей, недоступный сервер. Заменить общие `alert`.
- [ ] Блокировать повторную отправку кнопкой и проверкой `isLoading` в обработчике. После завершения запроса корректно сбрасывать состояние загрузки.

## 6. Конфигурация и удобство использования

- [ ] Импортировать `environment.ts` вместо `environment.development.ts`, чтобы работала замена конфигурации при production-сборке.
- [ ] Разрешить прокрутку страниц авторизации. Сейчас глобальный `overflow: hidden` может скрывать нижнюю часть регистрации на коротком экране.
- [ ] Проверить доступность всех полей и кнопки на телефоне, при открытой клавиатуре и показанных сообщениях об ошибках.
- [ ] Обновить инструкции запуска и настройки API в документации фронтенда.

## 7. Проверки перед сдачей

- [ ] Исправить тест, который ожидает удалённый стартовый заголовок `Hello, app`.
- [ ] Проверить точный payload регистрации, валидацию, ошибки API и блокировку повторной отправки.
- [ ] Проверить передачу настроек HTTP-клиентом, приватные запросы по умолчанию и публичные запросы без автоматического refresh.
- [ ] Проверить лимит в 3 повтора и отсутствие рекурсивного обновления.
- [ ] Проверить, что несколько одновременных запросов с истёкшим токеном вызывают ровно один refresh и затем продолжаются с новым токеном.
- [ ] Проверить запоздалый `401`, общую ошибку refresh и возможность следующего обновления после завершения предыдущего.
- [ ] Проверить guard, восстановление сессии и серверный logout.
- [ ] Запустить сборку и тесты: `npm run build`, `npm test -- --watch=false` из `/frontend`. Все проверки должны проходить.
- [ ] Пройти сценарии с настоящим бекендом: регистрация и вход → `/chats` → перезагрузка → истечение access token и refresh → выход → отказ в доступе к `/chats` без сессии.
- [ ] Отдельно проверить неверный пароль, занятые email/username, истёкшую или отозванную сессию и недоступность сервера.

Задача готова, когда перечисленные сценарии работают на компьютере и телефоне, код соответствует архитектурным правилам, а сборка и тесты проходят.
